# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SharpNotebook — a Jupyter Notebook clone for C#. Self-hosted, single-user, local-only tool. Full requirements and rationale for every architectural decision (why Blazor Server, why a hand-rolled Roslyn kernel instead of .NET Interactive, why no polyglot, etc.) live in `REQUIREMENTS.md` — read it before making architecture-level changes.

## Commands

```bash
dotnet build                                    # build all 5 projects (solution file: SharpNotebook.slnx)
dotnet run --project src/SharpNotebook.Web      # run the Blazor Server app (http://localhost:5000-ish, see launchSettings.json)
dotnet run --project src/SharpNotebook.Desktop  # run the Avalonia desktop app (native window, same ~/Documents/SharpNotebook notebooks)
dotnet test tests/SharpNotebook.Web.Tests       # bUnit component tests — no browser needed, see below
```

**Gotcha:** `SharpNotebook.Web` does not have a project reference to `SharpNotebook.Kernel.Host` (it can't — the kernel runs as a separate OS process, not a library call). Running `dotnet run --project src/SharpNotebook.Web` alone only builds Web + its transitive references (Core, Contracts); it will *not* rebuild Kernel.Host. Always `dotnet build` the whole solution first after touching Kernel.Host, otherwise the Web app spawns a stale kernel binary.

To exercise the kernel process directly without the web UI (useful for debugging the execution engine in isolation), pipe newline-delimited JSON requests into it:

```bash
printf '%s\n%s\n' '{"kind":"execute","cellId":"c1","code":"1+1"}' '{"kind":"shutdown"}' \
  | dotnet src/SharpNotebook.Kernel.Host/bin/Debug/net10.0/SharpNotebook.Kernel.Host.dll
```

## Architecture

Four runtime projects under `src/SharpNotebook.<Name>`, plus a test project under `tests/`:

- **`Core`** — notebook file model (`Notebook`, `Cell`, `CellType`) and `NotebookFile` (load/save `.sharpnb`, `System.Text.Json`, camelCase). No execution logic. A notebook's persisted `Cell.Outputs`/`ExecutionCount` are just the last-displayed transcript — reopening a notebook does not resume a live kernel, exactly like Jupyter.
- **`Kernel.Contracts`** — the IPC message types shared between `Web` and `Kernel.Host` (`ExecuteRequest`, `OutputDisplayEvent`, `ExecutionCompletedEvent`, etc.) plus `Protocol`, the `System.Text.Json` (de)serialization helper both sides use. Referenced by both.
- **`Kernel.Host`** — a console app. One process per open notebook. Owns a Roslyn `ScriptState<object>` chain (`ScriptSession.cs`) so variables/usings persist across cell executions like a REPL. Reads `KernelRequest`s from stdin, one JSON object per line; writes `KernelEvent`s to stdout the same way. Also owns the rich-display protocol — see below.
- **`Services`** — shared, UI-agnostic app logic used by both frontends: `NotebookSession` (spawns/owns one kernel process per open notebook, the stdin/stdout IPC loop) and `IAiCodeGenerator`/`OpenAiCodeGenerator` (OpenAI-backed AI cell). No ASP.NET or Avalonia dependency — plain BCL + `Microsoft.Extensions.Configuration.Abstractions`. Namespace `SharpNotebook.Services` (was `SharpNotebook.Web.Services` before this split).
- **`Desktop`** — Avalonia desktop frontend (second UI on top of the same `Core`/`Kernel.Contracts`/`Services`, started alongside the Blazor `Web` app rather than replacing it). `MainWindow.axaml.cs` is plain code-behind (no MVVM/ViewModels — matches this project's general "no unrequested abstraction" bias) that builds each cell's controls in C# (`BuildCellSlot`), not XAML `DataTemplate`s, since a notebook's cell list is dynamic and heterogeneous (Code/Markdown, dynamic type switching). Code editing uses `Avalonia.AvaloniaEdit`'s `TextEditor` + `AvaloniaEdit.TextMate` for C# syntax highlighting (`TextMateSharp.Grammars`, `RegistryOptions.GetLanguageByExtension(".cs")` → `SetGrammar`). `TextEditor.Text` is *not* kept synced to `Cell.Source` on every keystroke (no Monaco-style debounce needed) — it's pulled back via `SyncEditorsToCells()` right before any save/run/rebuild, since nothing reads `Cell.Source` in between. Known gaps versus the Web frontend, left for later: no AI cell type in the type selector, no nested folder browsing (flat root dir only), `text/html` output falls back to raw-text rendering (no HTML view control in Avalonia), no visual/screenshot verification possible in this sandboxed environment (no X server — smoke-tested only via a clean, exception-free timeout-limited run).

  **Feature set (kept close to parity with Web, plus a few Desktop-only extras):** multi-notebook tabs (each tab owns its own `NotebookSession`/kernel process — closing a tab disposes it), nested folder browsing in the sidebar (mirrors Web's `FileBrowser`), AI cell type (reuses `IAiCodeGenerator`, which calls the official OpenAI SDK's `ChatClient`, not a hand-rolled HTTP call; Desktop builds its own `IConfiguration` in `App.axaml.cs` since there's no ASP.NET host. The key comes from the `OPENAI_API_KEY` environment variable on **both** frontends — `IConfiguration`'s environment-variables provider picks it up automatically, no `appsettings.json`/user-secrets entry needed; set it in whatever shell/process launches the app before running), a Zmienne/Paczki side panel (new `VariablesRequest`/`PackagesRequest` kernel messages — `ScriptState.Variables` and `NuGetPackageResolver.Requested` exposed for this, see `Kernel.Contracts/Messages.cs` and `ScriptSession.GetVariables()`), export to `.cs`/`.html` via `StorageProvider.SaveFilePickerAsync`, a real (if narrow) `text/html` renderer (`HtmlRenderer.cs` — parses as XML, walks `<table>` into an Avalonia `Grid` and inline `<b>/<i>/<br>` into `TextBlock.Inlines`; anything that doesn't parse as XML falls back to tag-stripped plain text, since arbitrary user `Html(...)` calls aren't guaranteed well-formed), a Catppuccin Mocha/Latte light-dark toggle, an embedded JetBrains Mono font, and a hand-written Catppuccin TextMate token theme (`Assets/*.json`, embedded resources — not the upstream Catppuccin VS Code theme, which ships no static per-accent JSON in its repo; colors are hand-mapped from the same palette used everywhere else in this app). Drag-to-reorder cells exists (grip icon, press-drag-release) but only reorders on **release**, not live during the drag — a live-swap-mid-drag implementation would rebuild the visual tree while the dragged control still holds pointer capture, which Avalonia drops on detach and would silently break the gesture partway through.

  **Theming mechanism, if you touch colors again:** `App.axaml`'s `SolidColorBrush` resources are looked up ONCE per control via `StaticResource`, but they're *mutable* — the light/dark toggle (`ThemeToggle_Click`) doesn't swap which brush a control points at, it mutates the existing brush instances' `.Color` in place (`Application.Current!.Resources["CtpBaseBrush"]`), so every control sharing that instance repaints live with no rebuild. `MainWindow` caches these same instances into fields (`_base`, `_text`, etc.) in `CacheBrushes()` specifically so code-built controls (cells, output) share the identical objects rather than creating their own copies that the toggle can't reach. The one thing that mutation does *not* cover is TextMate token colors (syntax highlighting) — those come from a separate `IRawTheme` applied via `Installation.SetTheme(...)`, so the toggle also walks every open `CellSlot.Installation` and re-applies it explicitly.

  **This wasn't visually verified either** — same no-X-server constraint as the rest of Desktop. Verification here was: the whole solution builds clean, `dotnet test` still passes 7/7, a temporary `#if DEBUG_SMOKETEST` block (added, exercised, then removed — search git history if you need the exact diff) auto-opened a real notebook with existing text output on startup to confirm cell construction, font loading, and TextMate theme installation don't throw, and a standalone throwaway console project fed both embedded theme JSONs through `TextMateSharp`'s real `ThemeReader` to confirm they parse (13/13 token rules each, correct hex values round-tripped). None of that proves the layout *looks* right — only that it doesn't crash.

  **NuGet version landmine, worth reading before touching Desktop's `.csproj`:** the *old* NuGet package literally named `AvaloniaEdit` (0.10.12, all that's published under that id) is a dead end — its `AvaloniaEdit.TextMate` companion is hard-pinned to `TextMateSharp` assembly version `1.0.21.0`, but every published `TextMateSharp.Grammars` release (which is what actually ships the C#/markdown grammars) requires `TextMateSharp >= 1.0.25`, and no combination of versions satisfies both at once — you'll hit `CS0012: the type 'IRegistryOptions' is defined in an assembly that is not referenced` no matter which `TextMateSharp`/`TextMateSharp.Grammars` version you pin. The actual current, actively-maintained editor for modern Avalonia (12.x) is a *differently-named* package, `Avalonia.AvaloniaEdit` (still exposes the same `AvaloniaEdit` namespace/`TextEditor` type), paired with `AvaloniaEdit.TextMate` **12.0.0** (not 0.10.12 — same package id, unrelated version lineage) and `TextMateSharp`/`TextMateSharp.Grammars` **2.0.3**. That's the combination this project uses; don't downgrade `AvaloniaEdit.TextMate` back toward 0.10.x chasing an older tutorial.

- **`Web`** — Blazor Server (interactive server render mode). `Services/NotebookSession.cs` spawns and owns a `Kernel.Host` process per open notebook and speaks the stdin/stdout protocol to it; `RunCellAsync`/`GetCompletionsAsync` wrap the request/response loop for one cell so components don't duplicate it (both serialized through one `SemaphoreSlim` — see the completion section below for why). `Components/Pages/Home.razor` owns the open notebook + session lifecycle (a new `NotebookSession`, i.e. a fresh kernel, is started whenever a different file is opened) and registers the one page-wide Monaco completion provider (see below); `Components/FileBrowser.razor` navigates/creates/renames/deletes `.sharpnb` files under a root directory (defaults to `~/Documents/SharpNotebook`, overridable via `Home`'s `NotebooksRootDirectory` parameter — used by tests to avoid touching the real Documents folder); `Components/CellComponent.razor` renders one cell as a real Monaco editor (`BlazorMonaco.Editor.StandaloneCodeEditor` — see the Monaco section below) plus Run/output, and calls back up to `Home` to autosave after every edit/run; `Components/Icon.razor` is the shared hand-authored line-icon set (24x24 stroke SVGs — no emoji, no icon font). Visual system lives in `wwwroot/theme.css` (Catppuccin Mocha).
- **`tests/SharpNotebook.Web.Tests`** — bUnit component tests. They render the real `Home` component tree (real kernel process spawn, real Roslyn execution, real file I/O) and drive it via simulated DOM events, no browser required. This is the project's substitute for browser-based UI testing (no headless Chrome/Playwright available in this environment — see gotcha below).

### The kernel IPC protocol

Newline-delimited JSON over the child process's stdin/stdout — no `Content-Length` framing (unlike LSP), because it never leaves the local process pair. Message types are polymorphic via `[JsonPolymorphic]`/`[JsonDerivedType]` on `KernelRequest`/`KernelEvent` in `Kernel.Contracts/Messages.cs`, discriminated by a `"kind"` field. `Protocol.JsonOptions` uses camelCase + case-insensitive matching — get this wrong and fields silently deserialize as null/default instead of throwing (bit us once during development).

`NotebookSession.FindKernelHostDll()` locates the kernel binary by walking up from `AppContext.BaseDirectory` to find `*.sln`/`*.slnx`, then reconstructing `src/SharpNotebook.Kernel.Host/bin/<Config>/<TFM>/SharpNotebook.Kernel.Host.dll` using the *same* config/TFM segments the running Web app was built with. This only works if Kernel.Host was already built (see Gotcha above).

### The execution engine (`ScriptSession`)

Uses `Microsoft.CodeAnalysis.CSharp.Scripting` directly — not .NET Interactive. First cell: `CSharpScript.RunAsync`. Every following cell: `previousState.ContinueWithAsync`, which is what makes variables/`using`s survive between cells. `Console.Out` is swapped for a custom `TextWriter` (`EventStreamTextWriter`) for the duration of each execution so `Console.WriteLine` calls inside user code get forwarded as output instead of hitting the process's real stdout (which is reserved for the IPC protocol itself).

`ScriptEnvironment.cs` (not `ScriptSession` itself) builds the reference list and default `using`s, shared by both execution and completion — see the completion section below.

**Known footgun already hit once:** the output-forwarding callback must stay fully synchronous (plain `stdout.WriteLine`, no `async`/`.GetAwaiter().GetResult()` anywhere in that path). Wrapping it in an async call and blocking on it from inside `Console.WriteLine` deadlocks the kernel process — `Console.SetOut` wraps the writer in a synchronized `TextWriter`, and mixing that with a blocked-on-its-own-`Task` callback hangs. If you touch `EventStreamTextWriter` or the `onOutput` wiring in `Program.cs`, keep it synchronous.

### Rich output / display protocol

Every piece of cell output — stdout text, the last expression's value, an explicit `Display(...)` call, an error — ends up as one `OutputDisplayEvent(CellId, MimeType, Data)` (`MimeType` is `"text/plain"`, `"text/html"`, or `"image/png"` with `Data` base64-encoded). `Cell.Outputs` in Core (`List<CellOutput>`) persists exactly that; `CellComponent.razor` renders each by `MimeType` (`<pre>`, raw `MarkupString`, or `<img src="data:image/png;base64,...">`).

Formatting lives in `Kernel.Host/DisplayFormatter.cs`, driven by the *runtime type* of the value, not by any wrapping the user does normally:
- `Html` (a marker struct in `Kernel.Host/Html.cs`, in scope in every cell) → raw HTML. A bare `string` is never auto-rendered as HTML — wrap it in `Html(...)` first, otherwise it's plain text.
- `byte[]` → `image/png` (base64). Any charting library that can hand you PNG bytes works with zero library-specific code in this app — ScottPlot (referenced by `Kernel.Host`, `ScottPlot` is in the default imports) is the example: `plt.GetImage(w, h).GetImageBytes(ImageFormat.Png, 100)` as a cell's last expression renders inline. Note ScottPlot's own `Image.GetImageBytes()` overload with no format defaults to **BMP**, not PNG — you need the `(ImageFormat, int)` overload explicitly.
- any other `IEnumerable` → an HTML `<table>` (one column per public property of the element type, or one column of `ToString()` for scalars/anonymous types).
- anything else → `ToString()` as plain text.

A cell can call `Display(value)` (an instance method on `ScriptGlobals`, passed to Roslyn as the script "globals" object so it's unqualified in scope) to push extra output mid-cell using the same formatting rules, not just via the last expression.

### `#r "nuget:..."` (`NuGetDirective`, `NuGetPackageResolver`)

`NuGetDirective.Extract(code)` regexes out every `#r "nuget:PackageId"` / `#r "nuget:PackageId,Version"` line (Roslyn's own `#r` only understands file paths, not the `nuget:` scheme) and returns the code with those lines blanked out plus the parsed `(Id, Version?)` list. `ScriptSession.ExecuteAsync` calls this first, before anything else.

`NuGetPackageResolver` deliberately does **not** use `NuGet.Protocol`/`NuGet.Resolver` — reimplementing dependency resolution (transitive deps, version conflicts, framework-specific asset selection) by hand is a lot of intricate, easy-to-get-subtly-wrong machinery that `dotnet restore` already gets right. Instead: every `#r nuget` requested in the session accumulates into one throwaway `<PackageReference>`-only csproj under a per-`ScriptSession` temp dir; the resolver shells out to `dotnet restore` on it and parses the resulting `obj/project.assets.json` (`packageFolders` + `targets.<tfm>.<Id>/<Version>.runtime` asset paths, falling back to `.compile` for ref-only packages) to get real assembly paths under `~/.nuget/packages`, then `Assembly.LoadFrom`s each one. New assemblies get turned into `MetadataReference`s and added to **both** `ScriptSession`'s live `ScriptOptions` (execution) and `CompletionWorkspace`'s reference list (so a newly-added package's types show up in completion too, not just at runtime) — `_options`/`_references` had to become mutable per-instance fields instead of the static/shared-once state from M1–M4, since packages arrive mid-session.

A resolved `(Id, Version)` is only recorded as "already requested" in `_requested` **after** `dotnet restore` succeeds — recording it before, or on failure, means a retry of the exact same failing `#r` (typo fixed, transient network blip) would see it as "nothing new to do" and silently report success without ever actually resolving it. This was a real bug caught before it shipped, not theoretical — check for it if you touch `ResolveAsync`.

Restore errors (bad package id, network down, etc.) surface as a normal `OutputErrorEvent` in the cell, same as a compile error — but note `dotnet restore`'s actual NuGet diagnostics (e.g. `NU1101: Unable to find package`) go to **stdout**, not stderr; capture both or you'll get an empty error message on failure (happened once here too).

### Diagnostics and hover — kernel side (`CompletionWorkspace.GetDiagnosticsAsync`/`GetHoverAsync`)

Both reuse completion's own throwaway-submission-project trick (`AddSubmissionProject`, `finally`-removed) rather than introducing a second mechanism: diagnostics calls `Compilation.GetDiagnostics()` on the in-progress cell's project and maps each to `(Line, Column, Severity, Message)` (1-based, from `Diagnostic.Location.GetLineSpan()`); hover finds the token at a given offset, resolves it via `SemanticModel.GetSymbolInfo`/`GetDeclaredSymbol`, and returns `ToDisplayString(MinimallyQualifiedFormat)` plus the `<summary>` extracted from `ISymbol.GetDocumentationCommentXml()` if there is one. Desktop's `RefreshDiagnosticsAsync` only surfaces `Error`-severity results (not warnings) as a below-the-editor text summary, debounced 800ms after typing stops — this is deliberately not inline squiggle underlines, which would need a custom AvaloniaEdit render layer; a text summary is the bounded version of "see errors before you hit Run." Hover is wired through `TextEditor.PointerMoved` with a 500ms settle debounce and shown via `ToolTip.SetTip`/`ToolTip.SetIsOpen` on the editor itself, not a custom popup.

### Completion / IntelliSense — kernel side (`ScriptEnvironment`, `CompletionWorkspace`)

`ScriptEnvironment.cs` is the single source of truth for the reference assemblies and default `using`s — both `ScriptSession` (execution) and `CompletionWorkspace` (completion) build from `ScriptEnvironment.MetadataReferences`/`Imports`, so IntelliSense sees exactly what the code will actually run against.

`CompletionWorkspace` mirrors `ScriptSession`'s `ScriptState` chain as a chain of Roslyn "submission" `Project`s in an `AdhocWorkspace` (`isSubmission: true`, `hostObjectType: typeof(ScriptGlobals)`), because `CompletionService` needs a `Document` in a `Workspace` to run against — `CSharpScript` alone doesn't expose one. Each successfully executed cell calls `CommitCell(code)`, adding a permanent submission project chained (via `ProjectReference`) onto the previous one, exactly mirroring `ContinueWithAsync`. Each completion request adds one more throwaway submission project for the in-progress (not-yet-run) cell and removes it again in a `finally`.

`CompletionService.GetCompletionsAsync` returns *every* applicable symbol regardless of what's already typed — a real editor's own filter-as-you-type narrows it. Since nothing else does that narrowing here, `CompletionWorkspace.GetCompletionsAsync` scans backward from the cursor for the identifier prefix already typed and filters (`StartsWith`, ordinal-ignore-case) before returning. Skip this and completion lists are technically correct but useless (e.g. typing `x.ToStr` returns thousands of BCL members, `ToString` buried somewhere in the middle alphabetically, not surfaced by an `.Take(20)` on the caller side).

**The corlib bug — by far the worst debugging session in this codebase so far, worth reading in full before touching `ScriptEnvironment`/`CompletionWorkspace`:** completion silently returned wrong or empty results (fine for `Console.Wr` → members, empty for `x.ToStr` where `x` is a local `int`) with no exception. Root cause, found only by bisecting the ~200-assembly TPA-derived reference list down to individual assemblies and reflecting on `Assembly.GetReferencedAssemblies()`: `ScriptEnvironment`'s `Assembly.LoadFrom(path)` loop **silently fails to load `System.Private.CoreLib` at all** — its catch-all `catch { }` swallows the failure (corlib is already bound into the process by the runtime before any user code runs; asking to `LoadFrom` it again from its own TPA path throws). `CSharpScript` execution never noticed because Roslyn's scripting API has its own fallback reference resolver; a plain Workspace/`ProjectInfo` compilation (what `CompletionWorkspace` needs) has no such fallback, so *every* predefined-type lookup failed (`CS0518: Predefined type 'System.Object' is not defined`) — including inside completion's own diagnostics, which is why `CompletionService` returned nothing useful for anything that needed real type binding (member access) while still returning noise for symbol/keyword-list completion (which tolerates a broken compilation). The fix is the `.Prepend(typeof(object).Assembly)` in `ScriptEnvironment.ReferenceAssemblies` — reference the corlib the process already has loaded instead of trying to load it from disk again. If you ever see `CS0518` anywhere, a narrow reference allowlist is *not* the fix (that was a dead-end tried and reverted here) — check whether corlib is actually in the reference list first.

Two more real bugs the completion feature's own bUnit test (`CompletionTests.cs`) caught, unrelated to the above:
- `NotebookSession.RunCellAsync`/`GetCompletionsAsync` both do a `SendAsync` + `await foreach (ReadEventsAsync())` round-trip against the same process's stdin/stdout. Two overlapping calls on the same `NotebookSession` (e.g. a stray completion request firing while a cell is still running) throw `InvalidOperationException: The stream is currently in use by a previous operation on the stream.` Fixed with a `SemaphoreSlim _ioLock` around both methods' bodies — the kernel only processes one request at a time anyway, so the Web side should too.
- bUnit's own documented gotcha: `cut.Find(selector)` followed by `.Click()`/`.Change()` as two separate statements can race a re-render landing in between, invalidating the found element's event-handler ID (`UnknownEventHandlerIdException`). Fix: wrap `Find` + the trigger call together in one `await cut.InvokeAsync(() => cut.Find(selector).Click())`. Every UI test file uses this pattern now — keep doing it in new tests, it showed up as real (if intermittent) flakiness, not theoretical.

`NuGetTests.cs` covers `#r "nuget:..."` end-to-end through the real UI (real `dotnet restore` against `Newtonsoft.Json`, already in the local package cache so it's fast) — extend it rather than hand-testing when touching `NuGetPackageResolver`/`NuGetDirective`.

### Completion / IntelliSense — Monaco side (`Home.ProvideCompletionsAsync` / `BuildCompletionsAsync`)

Registered **once**, page-wide, in `Home.OnAfterRenderAsync(firstRender)`: `BlazorMonaco.Languages.Global.RegisterCompletionItemProvider(JS, "csharp", ProvideCompletionsAsync)`. Not per-cell — Monaco's completion providers are global per language, and registering one per `CellComponent` instance would stack a duplicate provider (and duplicate suggestions) for every cell that ever mounted, with no unregister hook to undo it. The provider is a plain `Func<string modelUri, Position, CompletionContext, Task<CompletionList>>` delegate (confirmed from BlazorMonaco's own `SampleWebApp/Pages/Index.razor.cs` — there is no `CompletionItemProvider` subclass to write despite a same-named type existing in the package; that type is for a different, class-based registration path this project doesn't use). The registered closure reads `_session` (a `Home` field) at call time, so it always targets whichever notebook is currently open, including after switching files — no per-cell model-to-session lookup needed. Monaco's own `modelUri` (unique per editor instance) is passed straight through to `NotebookSession.GetCompletionsAsync` as the "cell id" the kernel echoes back; it doesn't need to be the real `Cell.Id`, since nothing correlates on it beyond that one request/response round-trip.

`ProvideCompletionsAsync` is deliberately split from `BuildCompletionsAsync`: the former talks to Monaco (`Editor.Global.GetModel` + `model.GetValue()` to get the full text, converts line/column to a flat offset via `ToOffset`) and is unreachable in bUnit (no JS engine); the latter takes `(fullText, offset, lineNumber, column)` directly, calls the real kernel, and is `internal` (exposed to tests via `AssemblyInfo.cs`'s `[assembly: InternalsVisibleTo("SharpNotebook.Web.Tests")]`) precisely so completion logic stays testable without Monaco. If you touch either half, keep this split — folding them back together makes the kernel-calling logic untestable again for no benefit.

One BlazorMonaco quirk worth knowing before you go looking for a bug that isn't there: a `CompletionItem.RangeAsObject` you set in C# reads back as all-zero fields (`StartLineNumber`/`StartColumn`/etc.) if you inspect it directly afterward, outside of BlazorMonaco's normal C#→JSON→JS flow — confirmed by direct test (`CompletionTests.cs` used to assert on the returned range's fields; it now only asserts the range is non-null, because chasing the exact field values dead-ended in the library's own serialization plumbing, not a bug in this codebase). Trust that the *values you assign* are what get sent to Monaco; don't write tests that read them back through `RangeAsObject`.

### Monaco editor (`CellComponent`, BlazorMonaco 3.5.0)

**Real bug, already fixed:** cells rendered with no Monaco styling at all (garbled/unstyled code) because `App.razor` was missing the `<link>` for `_content/BlazorMonaco/lib/monaco-editor/min/vs/editor/editor.main.css` (~309KB) — `editor.main.js` does **not** self-inject this CSS (confirmed: zero style-injection calls in that file), and BlazorMonaco's own `jsInterop.js` even has an error message pointing at the missing *script* tag but nothing warns about the missing *stylesheet*. The three `<script>` tags (`jsInterop.js`, `loader.js`, `editor.main.js`) alone get you a functioning, unstyled editor — always pair them with this CSS link. Verified via `curl` (HTTP 200, correct byte count matching the file on disk, and the link tag present in the served HTML) rather than a screenshot, since this environment still has no browser — that's as far as verification goes here; if code still looks wrong after this fix, the next thing to check in a real browser is the browser's console for a 404/CSP error on that stylesheet, not this list.

Every cell — code *and* markdown — is a real `BlazorMonaco.Editor.StandaloneCodeEditor`, not a styled textarea. `EditorConstructionOptions` sets `Language` to `"csharp"` or `"markdown"` from `Cell.Type`; the `@key="@($"{Cell.Id}-{Cell.Type}")"` on the editor forces Blazor to destroy and recreate the whole component (not just re-render it) when the cell's type toggles, which is required — `ConstructionOptions` is only evaluated once, at construction, so an in-place type change would otherwise leave the editor's language stale.

`OnDidChangeModelContent` fires on *every keystroke* (unlike the old textarea's `onchange`, which only fired on blur). `Cell.Source` is updated immediately from `_editor.GetValue()` on each event (so `RunAsync` always sends the current text), but the `OnChanged` callback that triggers `Home.SaveAsync` (a real file write) is debounced 800ms via a cancel-and-restart `CancellationTokenSource`, so typing doesn't hit disk on every character.

API surface confirmed against BlazorMonaco 3.5.0's actual shipped assembly/source (its own README undersells the completion/theme pieces — verified via `strings` on the DLL plus the package's GitHub source, not guessed): `_editor.GetValue()` / `SetValue(text)` are `Task`-returning; `Editor.Global.GetModel(jsRuntime, modelUri)` returns a `TextModel` with `GetValue(eol, preserveBOM)` / `GetValueInRange(range, eol)` / `GetLineContent(lineNumber)`; `Editor.Global.DefineTheme(jsRuntime, name, StandaloneThemeData)` exists (`StandaloneThemeData { Base, Inherit, Rules: List<TokenThemeRule>, Colors: Dictionary<string,string> }`, `TokenThemeRule { Token, Foreground, Background, FontStyle }`) alongside `SetTheme(jsRuntime, name)`.

**Theme is Monaco's built-in `vs-dark`, not a custom Catppuccin-matched one — a deliberate, disclosed scope cut, not an oversight.** `Global.DefineTheme` exists and could produce an exact Catppuccin Mocha Monaco theme, but registering it safely has a real ordering dependency this environment can't verify: JS interop only works after a component's own `OnAfterRenderAsync(firstRender)`, and Blazor fires that callback bottom-up (children before parents) within a render batch — so a `DefineTheme` call from `CellComponent`'s own lifecycle would very plausibly run *after* its child `StandaloneCodeEditor` has already constructed itself referencing that theme name, in which case Monaco's real-world behavior is to silently fall back rather than error, meaning the failure mode is quiet, cosmetic, and specifically the kind of thing that needs a browser to notice. `vs-dark` needs no registration and is certain to render. If you pick this up later (with a real browser to verify against): the safe fix is almost certainly registering the theme once from `Home` (same place the completion provider is registered, same `OnAfterRenderAsync(firstRender)`, which — unlike a per-cell registration — reliably runs long before any cell exists, since cells only appear after a user opens a notebook).

### Testing the UI, updated for Monaco

Monaco raised the bar on what "no browser" costs here. `WebTestBase` (all UI test classes inherit it instead of `BunitContext` directly) sets `JSInterop.Mode = JSRuntimeMode.Loose` in its constructor — bUnit's default *Strict* mode throws `JSRuntimeUnhandledInvocationException` on any JS call it wasn't explicitly told to expect, and Monaco makes several during construction/disposal that there's no reasonable way to enumerate and mock one-by-one. Loose mode makes unconfigured calls return `default(T)` instead, which is enough for the surrounding Blazor/C# logic (execution, persistence, trust gating, restart) to keep running — it does **not** mean the editor itself renders or is exercised in any way; that half of the UI is genuinely untested here.

The practical fallout: bUnit has no real DOM to "type into" a Monaco editor. Every test that needs specific cell *content* now **pre-authors the `.sharpnb` file directly** (`new Notebook { ... }` + `NotebookFile.Save(path, notebook)`) instead of opening a blank cell and simulating keystrokes, then opens that file through the UI and clicks the real buttons from there. This still exercises the real pipeline end to end — `CellComponent.RunAsync()` sends `Cell.Source` to the kernel regardless of what the (unrenderable) editor shows — it just can't prove "a user typing into a live cell produces the right `Cell.Source`," because that link is now Monaco's `OnDidChangeModelContent`, which bUnit can't fire. `CompletionTests.cs` similarly no longer drives any dropdown UI (that UI doesn't exist anymore — see the Monaco completion section above); it calls `Home.BuildCompletionsAsync` directly via `cut.Instance`, which `AssemblyInfo.cs`'s `InternalsVisibleTo` makes reachable.

**A genuine race worth knowing about if you add a persistence assertion after a cell run:** `RunCellAsync`'s output callbacks fire (and update the DOM) *during* kernel execution, but the autosave (`OnChanged.InvokeAsync()` → `Home.SaveAsync` → a real file write) only happens in `RunAsync`'s very last line, after execution finishes. A `cut.WaitForAssertion` on the *rendered output text* can therefore pass before the file has actually been rewritten. If you're about to assert on `NotebookFile.Load(path)` right after such a wait, wrap that assertion in its own `cut.WaitForAssertion` too (poll the reload, don't read it once) — `HomeTests.cs` hit this for real, not hypothetically.

Two bUnit-specific gotchas hit while writing `HomeTests.cs`, both about now-removed textarea-era interactions but worth keeping in mind for the file-browser inputs (`new-notebook-name`, rename) that are still plain `<input>`s:

- An `<input>`/`<select>` bound with `@bind:event="oninput"` needs bUnit's `.Input(value)` to trigger a change, not `.Change(value)` (that fires `onchange`, which the element has no handler for and throws `MissingEventHandlerException`).
- Blazor Server renders a bound `<textarea>`'s value as a literal `value="..."` HTML attribute (non-standard, but that's how the diff gets serialized) rather than as child text content — moot now that cells don't use `<textarea>`, but the file-rename `<input>` in `FileBrowser.razor` still follows the same rule if you ever need to read it back in a test.

The persistence test also caught two real product bugs from the textarea era, both already fixed — worth knowing about if you touch the same code:
- `FindKernelHostDll` originally only searched for `*.sln`; the repo's solution file is `SharpNotebook.slnx` (new XML format), so it never found the kernel binary. Now searches for both.
- A newly-added Markdown cell defaulted to preview mode (`_previewing = true`), which hid the editor and made a brand-new empty markdown cell impossible to type into. New cells now default to edit mode.

`RichOutputTests.cs` covers the display protocol end-to-end through the real UI (table/HTML/image, including a real ScottPlot render) — extend it rather than hand-testing when touching `DisplayFormatter` or `CellComponent`'s output rendering.

**Visual verification of the Catppuccin theme (or anything Monaco renders) was not possible in this environment** — no headless browser (Node is v12, too old for current Playwright/Puppeteer; no Chrome/Chromium binary; no `claude-in-chrome` connection available in-session). Everything here was verified via source review, the mechanical `impeccable` design detector, and the bUnit suite above — never an actual screenshot. If you can run this in a real browser, that's the first thing worth doing before trusting the visual system further.

### Kernel lifecycle: interrupt, restart, trust (`NotebookSession.RestartAsync`, `Notebook.Trusted`)

There is no "interrupt" IPC message (see the comment above `KernelRequest` in `Messages.cs`) — the kernel's stdin-read loop is blocked inside `CSharpScript.RunAsync`/`ContinueWithAsync` while a cell executes, so a stuck cell (e.g. an infinite loop) can't be listening for anything sent over stdin, and Roslyn Scripting has no cooperative mid-execution cancellation to hook up even if it could. The only way to stop a stuck cell is `NotebookSession.RestartAsync()`: kill the OS process, spawn a fresh one. This is what both the "⏹ Przerwij" button (just the kill+respawn, cell outputs left as-is) and "🔄 Restart i uruchom wszystko" (kill+respawn, then `Home` re-runs every code cell top to bottom via `CellComponent.RunAsync()` — now `public`, called directly through `@ref`s in a `Dictionary<Guid, CellComponent>` keyed by `Cell.Id`) do in `Home.razor`.

`RestartAsync` doesn't take `_ioLock` itself and shouldn't — a cell stuck inside `RunCellAsync` is *holding* that lock while blocked reading the doomed process's stdout, so waiting for the lock before killing would deadlock. Killing the old process closes its stdout pipe, which unblocks that pending read (EOF/exception), which lets the stuck call's own `finally` release the lock normally — `RestartAsync` just needs to not get in that sequence's way.

`Notebook.Trusted` (Core) is `false` by default and only ever set `true` by `NotebookFile.CreateEmpty()` — i.e. only notebooks created through this app's own "Nowy" button start trusted. Since it's a plain missing-defaults-to-`false` JSON property, any `.sharpnb` authored or hand-edited outside the app (or predating this field) opens untrusted automatically, no migration/versioning needed. `Home.razor` shows a warning banner with a "Ufaj temu notebookowi" button when `!_notebook.Trusted`; `CellComponent`'s Run button is `disabled` (and `RunAsync` no-ops defensively even if called directly) while untrusted — completion is *not* gated, since resolving/showing completions never executes user code or triggers `#r nuget` resolution (only `ExecuteAsync` does).

`KernelLifecycleTests.cs` covers both: a real kill+respawn+re-run-all that proves cross-cell state really did come from a fresh kernel (not leftover process state), and a notebook written directly via `NotebookFile.Save` (bypassing the FileBrowser "Nowy" flow, so `Trusted` stays `false`) that must be explicitly trusted before its cell will run.
